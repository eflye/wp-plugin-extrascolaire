7,5/ 10 Note générale

La moyenne arithmétique des cinq dimensions donne 7,9. La note retenue est 7,5. Ce plugin a un profil en dents de scie : l'excellence est précisément là où les plugins WordPress s'effondrent d'ordinaire — la sécurité (zéro injection SQL, zéro XSS, garde nonce + capacité systématique) et l'usine à tests (une CI qui rejoue le produit réel dans WordPress + MySQL + Mailpit à chaque poussée).

Les retards se concentrent là où une mairie ne peut pas transiger : l'accessibilité d'un service public numérique (popins non conformes RGAA) et la couverture des chemins les plus risqués (migrations jamais exécutées avant la production, SIDSCM et facturation sans test). Et le seul trou de sécurité encore ouvert porte exactement sur ce que le plugin existe pour protéger : les noms, classes et régimes alimentaires de mineurs.

La trajectoire est bonne : le palier 1 — quelques heures de travail — ferme le constat critique et suffit à regagner 8 ; les paliers 2 et 3 ouvrent la voie vers 9.

01 · Architecture 8,0 /10 Socle propre, un seul point de croissance : Psc_Frontend.
02 · Sécurité 8,5 /10 Le point fort du code ; un trou de rate-limit sur le SIDSCM.
03 · Frontend & accessibilité 7,5 /10 Mécanique AJAX saine ; popins non conformes au RGAA.
04 · Données & installation 8,0 /10 Migrations soignées, mais zéro transaction SQL.
05 · Tests & outillage 7,5 /10 E2E exemplaire ; les trous touchent les chemins risqués.

Brute-force possible du code d'accès SIDSCM

Trois endpoints AJAX sur quatre — ajax_data, ajax_toggle, ajax_set_departure — n'appellent jamais psc_rate_limit_by_ip : seul ajax_unlock est protégé. Un attaquant qui énumère le code d'accès obtient les noms, classes et régimes alimentaires des mineurs, et peut falsifier les pointages.

Approbation des inscriptions non atomique

approve_request() crée le foyer, les enfants et les personnes autorisées en inserts successifs sans transaction — il n'en existe aucune dans tout le plugin. Un échec au milieu de la boucle perd un enfant en silence ; une réapprobation duplique les lignes.

Échecs d'ALTER silencieux

Une clé étrangère ou une contrainte CHECK refusée par l'hébergeur n'est signalée nulle part, et psc_db_version monte quand même : la mairie croit son schéma à jour. La fenêtre d'inscriptions est le pire moment pour le découvrir.

Popins sans sémantique de dialogue

Les cinq overlays s'ouvrent sans role="dialog", sans aria-modal, sans piège de focus (RGAA 7.1 / 7.3). Échap et clic extérieur existent déjà — il manque la sémantique attendue d'un service public numérique.

Les migrations ne tournent jamais avant la production

La CI réinstalle un site vierge : psc_db_version est posé directement à la version courante et les huit migrations n'ont aucune exécution automatisée. La première vraie exécution est celle de la mairie — et l'historique prouve que ce chemin cache des bugs.

Audit 01 · Socle & organisation

Architecture

8,0 /10

Un socle au-dessus du standard des plugins WordPress : décomposition admin exemplaire, helpers organisés par domaine, zéro code mort. Le seul point de croissance est le portail familial, jamais décomposé.

Forces

  • Décomposition admin exemplaire — Psc_Admin_Base::guard centralise la garde, une classe par domaine métier (v4.32.0) : le modèle à suivre pour le portail.
  • Helpers découpés par domaine, un fichier portant un critère unique — lisibilité et testabilité.
  • WP_Error généralisé dans les couches métier.
  • Zéro code mort détecté sur les 17 900 lignes parcourues.

Faiblesses majeures

  • Psc_Frontend non décomposé — 1 609 lignes, ~50 méthodes : le seul endroit du plugin où la complexité s'accumule encore.
  • Types de retour non contractualisés — un false signifie tantôt « absent », tantôt « erreur », tantôt « non autorisé ».

Faiblesses mineures

  • Motif de notice admin dupliqué dans ~12 templates.

Améliorations phares

  • Éclater Psc_Frontend sur le modèle admin (palier 3).
  • Contractualiser les retours — porté par phpstan niveau 3 (palier 2).
  • Helper psc_admin_notice (palier 2).
Audit 02 · Garde des données de mineurs

Sécurité

8,5 /10

La meilleure note de l'audit, et la plus rare dans l'écosystème : zéro injection, zéro XSS, et une garde capacité + nonce réellement systématique. Un seul trou subsiste — sur l'écran de pointage.

Forces

  • Zéro injection SQL, zéro XSS sur l'ensemble des requêtes préparées et des échappements vérifiés.
  • Garde capacité + nonce systématique sur ~88 handlers ; les endpoints anonymes des familles sont à triple verrou avec nonce dédié.
  • Justificatifs de mineurs stockés hors racine web, servis par un flux contrôlé.
  • Limitation de fréquence correcte derrière proxy, à fenêtre fixe (fiabilisée en v4.31.0) — là où elle est branchée.

Faiblesse majeure

  • Brute-force du code d'accès SIDSCM — 3 endpoints sur 4 sans rate-limit (class-psc-sidscm.php:172, 310, 363) : divulgation de noms, classes et régimes de mineurs, falsification des pointages. Le correctif tient en quelques lignes.

Faiblesses mineures

  • Pas de contrôle realpath() dans psc_private_path.
  • Pointage sans cohérence jour/service.
  • Téléchargements de justificatifs non journalisés.

Améliorations phares

  • Rate-limit sur les trois endpoints SIDSCM — priorité nº1 de tout l'audit (palier 1).
Audit 03 · Portails publics & conformité

Frontend, accessibilité, i18n

7,5 /10

Une mécanique frontend saine et honnête — progressive enhancement réelle, échappement systématique. La note plafonne sur deux angles que la mairie ne peut pas ignorer : la sémantique de dialogue des popins, et l'absence totale d'internationalisation.

Forces

  • Une seule mécanique AJAX — psc-ajax.js, zéro fetch ailleurs : un seul point d'entrée à auditer et à durcir.
  • Progressive enhancement assumée — les onglets sont de vrais liens serveur, le JS enrichit au lieu d'imposer.
  • Échappement HTML systématique côté JS (escapeHtml).
  • Enqueue conditionnel strict — pas de CSS/JS chargé pour rien.
  • Calendrier bien balisé — caption, th scope, aria-label riches.

Faiblesses majeures

  • Popins sans sémantique de dialogue — aucun role="dialog" ni aria-modal, focus non piégé, sur les 5 overlays (RGAA 7.1 / 7.3).
  • i18n totalement absente — 0 appel à ()__, et un en-tête Text Domain mensonger. Sans conséquence pour une mairie mono-langue ; coûteuse à retro-fit si le plugin se diffuse.

Faiblesses mineures

  • aria-live absent sur les totaux.
  • prefers-reduced-motion ignoré.
  • Contrastes limite — boutons dorés ~3:1.

Améliorations phares

  • Sémantique de dialogue des 5 popins (palier 2).
  • i18n complète — décision stratégique selon la diffusion (palier 3).
Audit 04 · Schéma, migrations, cycle de vie

Données & installation

8,0 /10

Des migrations versionnées et idempotentes, un schéma contraint et documenté, un uninstall par découverte qui corrigeait dix tables oubliées. Deux faiblesses majeures tiennent au même refus : ne jamais admettre qu'une écriture ou un ALTER peut échouer.

Forces

  • Migrations versionnées idempotentes — psc_db_version découplé de PSC_VERSION, dbDelta avant migrations.
  • FK et CHECK posées avec justifications documentées — le schéma se lit comme un texte de décision.
  • Uninstall par découverte — il corrigeait 10 tables oubliées sur 16.
  • Temps testable — psc_now_ts filtrable, clé du déterminisme de la CI.

Faiblesses majeures

  • Aucune transaction SQL dans tout le plugin — approve_request() (class-psc-requests.php:632) écrit foyer + enfants + personnes en boucle non interrompue : enfant perdu en silence, duplication à la réapprobation.
  • Échecs d'ALTER silencieux — FK/CHECK refusées jamais signalées, psc_db_version monte quand même (class-psc-installer.php:264-367).

Faiblesses mineures

  • N+1 sur l'écran des inscriptions — ~60 requêtes par trimestre.
  • Purge RGPD ~2 h trop tôt — mélange current_time/gmdate (class-psc-requests.php:60-77).
  • Cron dépendant des visites du portail.
  • Rôles en dur dans uninstall.

Améliorations phares

  • Transaction autour de approve_request() (palier 2).
  • Health-check admin des contraintes manquantes (palier 2).
  • GROUP BY pour le N+1 (palier 1).
Audit 05 · Filet de sécurité & livraison

Tests, outillage, CI & release

7,5 /10

Une suite E2E d'une qualité rare — le produit réel, dans WordPress + MySQL 8 + Mailpit, à chaque poussée, horloge figée, assertions en base et dans les e-mails. Mais zéro couche rapide en dessous, et des trous précisément là où le risque se concentre : migrations, SIDSCM, facturation.

Forces

  • La CI teste le vrai produit — stack Docker complète, installation WP réelle sous www-data, exécution à chaque poussée et PR ; l'en-tête du workflow documente les classes de pannes qui l'ont motivée.
  • Déterminisme par conception — horloge figée via psc_now_ts, ancre temporelle cherchée dynamiquement pour que la suite passe toute l'année, exécution séquentielle justifiée.
  • Des assertions qui vérifient la vérité, pas l'écran — lecture directe de la base, e-mails lus via Mailpit, assertions négatives, pièges dans les seeds : 10 scénarios, 138 expect(), 1 543 lignes d'infrastructure.
  • Deux scripts verify-*.php avec vraies assertions en WP-CLI réel — l'un a déjà attrapé des bugs de migration en conditions réelles.
  • Release avec garde-fou — tag refusé s'il ne correspond pas à PSC_VERSION ; matrice lint PHP 7.4 → 8.3.

Faiblesses majeures

  • Les migrations n'ont aucune couverture automatisée — psc_db_version posé à neuf à l'activation, la CI ne rejoue jamais le chemin de mise à jour de la mairie (class-psc-installer.php:9-16).
  • SIDSCM, facturation, export, purge RGPD, uninstall : zéro test — ~20-25 % de la surface HTTP couverte (15-18 endpoints sur 77 points POST).
  • Zéro test unitaire, zéro analyse statique — banking.php et crypto.php sont pourtant testables sans WordPress ; psc-ajax.js, passerelle unique de tous les appels, n'a ni test ni lint.
  • Les verify-*.php ne tournent pas en CI — le meilleur de l'outillage existant tient à la discipline manuelle du mainteneur.

Faiblesses mineures

  • Lint réduit à php -l.
  • WP 5.8 minimal annoncé, jamais testé (wordpress:latest uniquement).
  • Zip de release jamais fumé, liste de fichiers maintenue à la main.
  • Pas de concurrency, pas de changelog produit.

Améliorations phares

  • Brancher les verify-*.php en CI — le gain le plus rapide de tout l'audit (palier 1).
  • E2E SIDSCM + scénario de migration (palier 2).
  • phpstan niveau 3, tests unitaires des helpers purs (palier 2).
